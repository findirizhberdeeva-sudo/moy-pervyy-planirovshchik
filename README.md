# Ритм

[Открыть «Ритм»](https://findirizhberdeeva-sudo.github.io/moy-pervyy-planirovshchik/) · [Исходники на GitHub](https://github.com/findirizhberdeeva-sudo/moy-pervyy-planirovshchik).

Pages включён из main/docs; HTTPS-страница и экран входа проверены. Edge развёрнута, оба подтверждённых аккаунта созданы и подключены к одной команде. SMTP по решению пользователя не используется. Точный статус и ограничения приёмки — в QA.md и ACCEPTANCE.md.

Командный планировщик по `tz.md` 1.4. Реализованы доступ, календарь задач, команда, комментарии, уведомления, синхронизация, автоматизация и отчёты. Выполняется облачная приёмка шага 5. Проект Supabase создан, первые 13 миграций применены в новой базе, затем добавлена миграция 014 личной динамики; RLS включён на всех таблицах. Auth настроен для закрытого входа, Edge развёрнута; рабочая команда создана, основные RPC и права проверены на настоящем PostgreSQL; настоящая сессия руководителя, Edge и рабочий PPTX проверены; настоящие сессии обеих ролей и ограничения интерфейса проверены; доставка контрольного изменения между ними ещё проверяется; письма в текущем режиме выключены. Исходный app.js содержит пустую конфигурацию, а папка docs — три файла с публичными параметрами для Pages. Локальной имитации командной доски в продукте нет.

Основной планировщик включает день, семидневную неделю и месяц, быстрое и полное создание, назначение, направления, приоритеты, сроки, статусы и длительные задачи. Доступны поиск, фильтры, группировка, перенос через меню и мышью, история, отмена, повторное открытие, корзина и восстановление. Прогресс рассчитывается SQL-функциями с учётом исторического плана. Добавлены управление сотрудниками и приглашениями, комментарии, личные уведомления, повторения и ежедневный перенос. Реализованы итоги и экспорт PPTX/PNG/текста. Полная облачная приёмка остаётся в шаге 5.

Оформление по уточнению пользователя: Rubik, увеличенные на 2 px основные размеры текста, тёплая оливковая палитра, цветовые акценты периодов и крупное оранжевое приветствие. Процент и полоса прогресса меняют цвет от приглушённого розового к зелёному. В styles.css подключены кириллица и латиница Rubik с Google Fonts (`fonts.gstatic.com`); `font-display: swap` сохраняет видимый текст во время загрузки, при недоступности используется системный шрифт. Дополнительных файлов интерфейса не требуется.

## Локальный просмотр

Нужен Node.js 22 или новее.

```sh
npm ci
npm run dev
```

Открыть адрес, напечатанный сервером: `http://127.0.0.1:3000/`. Сервер публикует только index.html, styles.css и app.js. Служебные файлы и зависимости через него недоступны.

## Проверки

```sh
npm run check
npm test
npm run test:browser
```

Для браузерных тестов используется установленный Chrome на Windows. Другой путь можно передать переменной `RITM_BROWSER_PATH`. Для других систем требуется браузер, совместимый с Playwright. В ограниченном окружении запуск браузера и обращение к localhost требуют разрешения на локальную сеть.

SQL-тесты выполняют все 15 настоящих миграций в изолированной PostgreSQL WASM (PGlite). Отдельный тест закрывает и заново открывает файловую БД, проверяя сохранение задачи и истории. Auth-таблица и личность запроса задаются тестовой средой. Браузер использует тестовые HTTPS-ответы Auth, настоящий SQL всех RPC, производственный обработчик Edge Function и тестовый сервер протокола Realtime. Это не проверка развёрнутого Supabase, криптографической проверки JWT или доставки писем. В приложении тестовых ответов и учётных записей нет.

## Подключение настоящего проекта

1. Создать отдельный проект Supabase. Административный доступ и SMTP-пароли не вставлять в app.js или чат.
2. Применить SQL-файлы `supabase/migrations` по имени в порядке возрастания от имени владельца миграций. Миграции рассчитаны на новую базу проекта; повторное применение уже выполненной миграции не требуется.
3. В Supabase Auth включить вход по email/паролю, выключить свободную и анонимную регистрацию, установить минимум 12 символов. Для текущего запуска без почты выключить Secure password change, чтобы смена своего пароля не требовала письма с nonce. В почтовом режиме включить её и установить срок Email OTP 86400 секунд. Значения и шаблоны приведены в `supabase/config.toml` и `supabase/templates`. TOML настраивает локальный Supabase; управляемый облачный проект сам от наличия этого файла не настраивается.
4. Настроить Site URL и точные Redirect URL. Текущий запуск — без SMTP и писем: RITM_EMAIL_DELIVERY_ENABLED=false в сборке и функции. Создать подтверждённые аккаунты вручную, как описано ниже. Только при явном переходе в почтовый режим настроить SMTP и переключить обе настройки в true. Для GitHub Pages адрес включает путь репозитория и завершающий `/`. Восстановление и приглашения используют `token_hash`; приложение убирает его из адресной строки до загрузки SDK.
5. Создать подтверждённую учётную запись первоначального руководителя в Auth и установить ей пароль. Через SQL Editor от имени владельца вызвать `private.bootstrap_team` с настоящими email, именем и названием команды. Функция доступна только администратору и откажется создавать вторую команду. Из браузера назначить себе роль руководителя нельзя.
6. Для выпуска задать публичные RITM_SUPABASE_URL, RITM_SUPABASE_PUBLISHABLE_KEY и RITM_APP_BASE_URL по инструкции публикации ниже. Можно сохранить их в игнорируемый .env.local и выполнить `node --env-file=.env.local scripts/build-release.mjs --pages`. Исходный Config остаётся шаблоном, публичная конфигурация подставляется в docs/app.js. Публичный ключ должен быть publishable либо legacy JWT с ролью anon; административный ключ не допускается.
7. Подключить Edge Function, Realtime и Cron по инструкции ниже. После подключения выполнить отдельные проверки настоящих Auth, RLS, конкурентных транзакций, WebSocket и расписания; почта проверяется лишь при её включении. Пройденные локальные тесты их не заменяют. Публикация относится к шагу 5.

При включённой безопасной смене пароля Auth может потребовать свежий вход: пользователь выходит и входит повторно, затем меняет пароль. Приложение сообщает о необходимости повторного входа.

## Хранение и права

В облаке подготовлены 13 таблиц ТЗ, включая закрытые историю, приглашения и результаты операций. На таблицах включён RLS, прямые браузерные записи запрещены. Роль и активность проверяются по базе, а не по данным localStorage.

Браузеру доступны `get_access_context`, `update_profile`, `activate_invited_member`, `get_planner`, `get_task_detail`, `get_task_history`, `list_task_collection` и `mutate_task`. Последняя функция объединяет логические команды ТЗ: `create` → create_task, `update` → update_task, `move` → move_task, `status` → change_status, `delete` → delete_task, `restore` → restore_task, `take_control` → take_task_control. Все мутации принимают ключ операции; изменение существующей задачи также требует ожидаемую версию. Названия таблиц соответствуют ТЗ.

`get_planner` возвращает один согласованный снимок дня, недели, месяца и прогресса. Функции чтения ограничивают частоту запросов, а расчёт выполняют внутри отдельной STABLE-функции. История и журнал плановых дат закрыты для прямого чтения/изменения клиентом. Лимиты и полномочия проверяются SQL, независимо от состояния кнопок интерфейса.

SDK сохраняет локальную сессию входа; пароль не сохраняется. Фильтры и группировка сохраняются отдельно для пользователя и команды; поисковая строка не сохраняется, после входа дата снова сегодняшняя. Если браузер блокирует хранилище, сессия живёт в памяти до закрытия страницы и показывается соответствующее сообщение. Рабочие данные не подменяются localStorage. Черновики живут в памяти страницы; при сетевой ошибке остаются, но при закрытии браузера не восстанавливаются. Скрытой очереди офлайн-изменений нет.

## Подключение шага 3

1. Применить оставшиеся миграции 007–011 после уже выполненных 001–006. В новой базе применять все 15 по порядку, включая отчётную миграцию 012, оптимизацию календаря 013 и личную динамику 014. По-прежнему используются 13 таблиц ТЗ; добавлены служебные поля версий/генерации и доставки, отдельные бизнес-сущности не вводились.
2. Развернуть `supabase/functions/team-admin`. Файл `index.ts` — оболочка Deno, `handler.mjs` — общий обработчик, исполняемый также тестами. Импорт SDK зафиксирован на 2.118.0. В конфигурации функции `verify_jwt=false`: проверку выполняет сам обработчик через Auth.getUser, затем проверяет действующую роль в БД, и лишь после этого создаёт административный клиент.
3. В хранилище секретов Supabase задать `RITM_APP_URL` — полный URL страницы с путём репозитория и завершающим `/`; `RITM_ALLOWED_ORIGINS` — точные origin через запятую, без пути и завершающего `/`. Для рабочей публикации разрешается её HTTPS-origin; localhost/127.0.0.1 добавлять только для нужной локальной разработки. Пустой пример — `supabase/functions/.env.example`. Функция использует предоставленные средой SUPABASE_URL, SUPABASE_ANON_KEY и SUPABASE_SERVICE_ROLE_KEY; служебный ключ никогда не копируется в app.js или публикуемые настройки.
4. Для текущего запуска оставить RITM_EMAIL_DELIVERY_ENABLED=false: приглашения сервером запрещены, SMTP не нужен. Далее описан только дополнительный почтовый режим: включить true и настроить SMTP и служебные шаблоны Auth из шага 1. Приглашение нового/неподтверждённого пользователя использует Auth Admin inviteUserByEmail. Если подтверждённая Auth-учётная запись ещё не вступила в команду, повторная настройка выполняется восстановлением пароля; установка пароля завершает активацию существующего действующего приглашения. SQL требует новый пароль относительно момента приглашения, подтверждённую личность и срок 24 часа.
5. Миграция 011 добавляет только `public.teams` в публикацию `supabase_realtime`, сохраняя прочие таблицы существующей публикации. Изменение номера версии вызывает перечитывание разрешённых DTO. Тексты комментариев и закрытый журнал в публикацию не добавляются. При отключении участника последующая проверка доступа закрывает интерфейс независимо от оставшегося JWT.
6. При доступном pg_cron миграция создаёт расширение и настраивает задание переноса `ritm_daily_maintenance`: `0 21 * * *`, UTC/GMT, вызов `private.maintain_all_teams()`. Повторный вызов владельцем `private.configure_daily_cron()` обновляет задание с тем же именем. Не выставлять часовой пояс Cron в Europe/Moscow при этом UTC-расписании.
7. После развёртывания проверить реальную отправку/повтор/отмену приглашения, вход с другого устройства, отключение и передачу, подписку, потерю связи и фактический запуск Cron. Модель WASM не содержит pg_cron: миграция честно сообщает о недоступном расширении; локальный успех не подтверждает установленное облачное расписание.

Доставка Auth и транзакция БД не объединяются. Намерение отправки, lease на 60 секунд и результат сохраняются до/после внешнего вызова. Потеря ответа фиксации повторяет только фиксацию. Неизвестный итог внешнего вызова отображается как неподтверждённая отправка, а не «Отправлено»; повтор после истечения lease продолжает то же приглашение. Гарантия ровно одного письма при аварии между SMTP и фиксацией не обещается. Участник остаётся приглашённым до подтверждённого связывания и активации.

При отключении сначала атомарно передаются активные задачи/будущие серии и закрывается членство, затем обновляется блокировка Auth. Если Auth недоступен, данные уже закрыты RLS, а интерфейс предлагает повтор настройки входа. Старый повтор сверяется с текущим членством и не отменяет более новое включение/отключение.

## Операции и автоматизация шага 3

| Физический вызов | Логические операции ТЗ |
| --- | --- |
| Edge `team-admin`: action | invite_employee, resend_invitation, cancel_invitation, list_team_admin, disable_employee, enable_employee |
| `mutate_comment`: create/update/delete | create_comment, update_comment, delete_comment |
| `list_comments` | Страницы по 50, устойчивый курсор ID, быстрый переход к последним 50 |
| `get_notifications`, `read_notifications` | Личные записи, фильтр чтения, страница по 50; чтение IDs либо всех не новее времени снимка |
| `mutate_series`: create/update/stop | Создание серии, update_series, stop_series; boundary задаёт «эту и будущие» либо будущие от сегодня |
| `preview_series` | Разрешённое правило и число уже созданных затрагиваемых экземпляров перед подтверждением |
| `sync_workspace` | Серверное сегодня, восполнение, актуальная версия; без клиентской даты выполнения |

«Только эту задачу» использует обычный mutate_task и не меняет шаблон. «Эту и будущие» и «Изменить будущие повторения» отправляют mutate_series с границей исходного расписания не раньше сегодня. Для законченного правила функция обновления недоступна; восстановление остановленного расписания как отдельная возможность в ТЗ не предусмотрено.

Версии правил закрыты в series_revisions. Для лениво созданного экземпляра effective_created_at и события включения отражают время появления правила; created_at/recorded_at — фактическую вставку. Будущий просмотр не двигает сегодняшнюю дату. Автоперенос меняет тот же ID на однодневное продолжение, восполняет пропущенные рабочие даты и сохраняет статус/срок. Управление временем тестов не публикуется в RPC.

После входа выполняются проверка доступа, sync, снимок плана и подписка. Повтор той же версии игнорируется. Восстановление подписки, сети, возврат вкладки и проверка каждые 60 секунд перечитывают данные. Форма не заменяется внешней записью: показываются актуальный вариант и черновик; подтверждённый повтор применяет только действительно изменённые разрешённые поля.

Для наблюдения владельцем БД доступны `teams.maintenance_checked_at`, `maintenance_result`, `maintenance_last_error_code`, `maintenance_failed_at` и `last_processed_date`. Результат maintain_all_teams содержит обработанные команды, уникальные перенесённые задачи, новые экземпляры и безопасные коды ошибок. При ошибке дата успешной обработки не продвигается; следующий проход восполняет пропуск. Проверять и статус задания Cron, и прикладной результат команды: ошибки отдельных команд перечисляются отдельно.

Состояние разработки и ограничения фиксируются в plan.md, проверки — в QA.md. Кэш, node_modules, результаты тестов и .env исключены из Git.

## Итоги и отчёты — шаг 4

После миграций 001–011 применить 202611010012_reports.sql. Новых таблиц нет: используется предусмотренная ТЗ private.report_snapshots. Периоды и метрики считаются сервером по истории, а не по загруженным карточкам. Общий результат не усредняет проценты сотрудников. Группы по неделям ограничены выбранным месяцем; сумма подпериодов не является итогом периода.

- get_report(p_team_id, p_period_type, p_period_start, p_employee_id, p_direction) создаёт снимок на 24 часа. Только employee_id и direction из фильтров плана влияют на отчёт. Нормализация недели — понедельник; месяца — первое число.
- get_report_rows(p_snapshot_id, p_metric_key, p_cursor, p_limit, p_scope) возвращает до 50 строк замороженного набора. p_scope по умолчанию all, либо возвращённое API значение employee:UUID, direction:код, period:дата для расшифровки строки таблицы. Курсор — смещение в неизменяемом, отсортированном по UUID массиве. Прогресс раскрывает числитель выполнения плана.
- get_export_data(p_snapshot_id) выдаёт весь DTO со списками фактических завершений и просроченных задач, без обрезки и внутренних наборов расшифровок. Все чтения проверяют автора снимка и действующее членство.

Показатели и экспорт остаются одним снимком после Realtime-изменений: появляется предложение обновить итоги. Это не создаёт новый отчёт каждую минуту. Новый снимок ограничен 6 запросами в минуту на пользователя и 30 в час на команду, с точным временем повтора; получение существующего относится к обычному чтению. Истёкший снимок предлагает обновление с сохранёнными фильтрами.

PPTX создаётся в браузере закреплённым bundle PptxGenJS 4.0.1 с JSZip из jsDelivr, загружаемым один раз при первом экспорте; после ошибки возможен повтор. devDependency той же версии нужна только для проверки настоящего bundle. PNG использует Canvas 1920×1080, без DOM-скриншота и стороннего генератора; текст использует Clipboard API с выделяемым резервным полем. В файлы не входят email, комментарии и закрытый журнал. Blob URL освобождается через 60 секунд после запуска сохранения. Фактическое завершение системного сохранения браузер не подтверждает, поэтому интерфейс сообщает лишь о подготовке файла.

Таблицы PPTX — редактируемые объекты: шрифт Arial 12 pt, переносы по измеренной ширине, до 10 строк и 5,1 дюйма основной области; слишком высокая строка делится с сохранением внутреннего ID. Страницы рассчитываются заранее, заголовки и номера повторяются. Служебная нормализация пакета убирает только ссылки Content_Types на несуществующие дополнительные slideMaster, которые объявляет bundle 4.0.1; существующие части и содержимое слайдов не меняются.

Отчёты проверены в настоящем Supabase. Контрольный PPTX импортирован в нативный Google Slides: сохранены 6 слайдов, таблицы и текст; все страницы экспорта PDF Google просмотрены. Сохранение правки непосредственно в Google / PowerPoint не подтверждено. Локально дополнительно проверяются структура OOXML, редактируемые таблицы и геометрия.

## Публикация из main

Приёмка и незакрытые условия: ACCEPTANCE.md и QA.md. Подробная история — plan.md. Для рабочей публикации нужны настоящий Supabase, Auth и окончательный HTTPS-адрес Pages. SMTP не требуется в текущем режиме без писем.

Сборка читает публичные переменные RITM_SUPABASE_URL, RITM_SUPABASE_PUBLISHABLE_KEY, RITM_APP_BASE_URL и RITM_EMAIL_DELIVERY_ENABLED (по умолчанию false; допустимы только true/false). Последняя включает подпапку репозитория и завершающий /. Без этих значений npm run build и npm run prepare:pages завершаются ошибкой; секретные ключи не допускаются. Исходный app.js при сборке не меняется.

Команда npm run build готовит dist для проверки; npm run prepare:pages готовит docs. В каждую папку записываются только index.html, styles.css и app.js. Папка с посторонними файлами не публикуется и не очищается автоматически. Результат сборки содержит SHA-256 трёх файлов, без вывода ключа. Перед выпуском изменения источника требуют повторной сборки.

Для запрошенного пользователем варианта GitHub Pages: добавить три файла docs в main, выбрать Settings → Pages → Deploy from a branch → main → /docs. Папка исходного проекта целиком в Pages не публикуется; пользователь отдельно разрешил публичный репозиторий исходников. После появления окончательного адреса тот же адрес задаётся в Auth Site URL/Redirect URLs и RITM_APP_URL; origin — в RITM_ALLOWED_ORIGINS. Проверка реальных ссылок и расписания не заменяется проверкой локального пути. [Официальная инструкция](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site).

CI .github/workflows/ci.yml проверяет серверные тесты и три тестовых движка в Ubuntu; публикацию из ветки он не подменяет. Локально RITM_BROWSER_ENGINE выбирает chromium / firefox / webkit. На Windows Chrome/Edge задаются RITM_BROWSER_PATH; тестовые Firefox/WebKit устанавливаются Playwright. Настоящие Safari/iOS/Android и предыдущие основные версии проверяются отдельно.

Контрольный набор: node scripts/benchmark.mjs создаёт только изолированную WASM-базу с 20 участниками, 10 000 задач и 100 000 событий; ни к какому облаку не подключается. Тестовые адреса example.test, бизнес-данные не используются. Результат — .cache/step5-scale.json; это не замер настоящего облака или сети. Карта 48 UC/39 AC обновляется командой node scripts/acceptance.mjs.


## Текущий запуск без почты: руководитель и помощник

SMTP и почтовые шаблоны не настраиваются. В Auth → Sign In / Providers отключить самостоятельную регистрацию и анонимный вход; Email/password оставить включённым. Минимум пароля — 12; Secure password change выключить, чтобы не требовалось почтовое подтверждение смены пароля. Сохранённая сессия и проверка действующего членства обязательны.

В Auth → Users → Add user → Create new user владелец по очереди создаёт два аккаунта с Auto Confirm User. Email вводится только в Supabase; человек сам вводит и отправляет пароль. Руководителю назначается команда через private.bootstrap_team. Затем владелец добавляет помощника в public.team_members с UUID подтверждённого Auth-пользователя, team_id созданной команды, display_name, role='employee', state='active'; схема и ограничения миграций сохраняются. Повторно bootstrap_team не вызывать. Служебные Auth-таблицы через SQL не менять.

Если пароль утрачен, владелец восстанавливает его в Supabase; приложение не обещает письма или автоматическую ссылку. Новый пароль человек вводит и отправляет сам; пароль не публикуется и не передаётся ИИ. При действующем входе пользователь может менять свой пароль в профиле.

В сборке и Edge задать RITM_EMAIL_DELIVERY_ENABLED=false. Форма приглашения и список приглашений скрыты, сервер возвращает EMAIL_DELIVERY_DISABLED для invite_employee / resend_invitation до создания привилегированного клиента. Просмотр команды, отключение с передачей задач и включение участника остаются доступны руководителю.


## Публичный код и закрытые рабочие данные

Публичный репозиторий разрешает читать и копировать исходники и документацию. Задачи и пароли пользователей в Git не хранятся. Публичный ключ Supabase предназначен для браузера; доступ к данным требует действующего входа и членства, проверяется облаком. Секретные/admin ключи, SMTP-пароли, реальные пароли и рабочие выгрузки нельзя добавлять в Git, даже в private-репозиторий. Перевод в private на GitHub Free автоматически отключает GitHub Pages; доступ к базе этим не настраивается.

## Личная динамика и поддержка — дополнение ТЗ 1.3

После 001–013 применить `202611020014_daily_support.sql` один раз. Новых таблиц нет: тип `daily_support` расширяет личные notifications. Новое задание `ritm_daily_support` — `45 14 * * 1-5` в UTC/GMT, то есть 17:45 Москвы по будням; ежедневный перенос сохраняет прежнее расписание. Миграция проверяет часовой пояс Cron. В WASM расширения Cron нет, проверяется логика с управляемым временем; настоящее исполнение расписания проверяется отдельно.

`get_weekly_progress(p_team_id)` возвращает текущую серверную неделю из семи дней, числа плана/выполнения по существующей исторической формуле и последний доступный поддерживающий итог. Сотрудник получает только себя; руководитель — себя и активных сотрудников. Фильтры списка не меняют эти данные. Пустой план не получает выдуманного процента. Незавершённый план с округлёнными 100% не считается полностью выполненным.

`claim_daily_support(p_team_id,p_notification_id)` атомарно отмечает собственный итог показанным. Независимые сессии не получают два успешных подтверждения показа. Скрытая вкладка/открытый диалог не начинают запрос показа. Потеря ответа может пропустить всплытие; постоянная карточка и уведомление сохраняются. Руководителю всплывает его собственный итог, сообщение сотрудника видно в карточке и центре уведомлений с независимым прочтением.

До 17:45, в выходные и после пропуска нескольких дней выбирается один последний завершённый рабочий день; дни до вступления в команду исключены. Позднее выполнение в тот же день обновляет текст, не сбрасывая read_at. Идентичное обновление не меняет уведомление и не создаёт цикл Realtime. Чтение, первый вход и обычное обновление восполняют пропущенный запуск; текст и дата определяются сервером. Ошибка дополнительного RPC не блокирует основную доску и оставляет кнопку повтора.

Проверки дополнения: `node --test tests/daily-support.test.mjs` и `npx playwright test tests/browser/daily-support.spec.mjs`. Среда и фактические результаты — в QA.md; история — в plan.md. Реальные задачи и административные ключи в исходники не включаются.
