# Техническое задание: командный планировщик «Ритм»

Версия: 1.4. Дата: 2 ноября 2026 года. Язык продукта и документации: русский.

Документ определяет функциональность первой версии, права, сценарии, данные, расчёты, технические контракты и приёмку продукта.

Уточнение 1.4 (разделы 10.2 и 23): результат считается по сроку сдачи, без срока — по последнему дню работы, с ежедневным учётом незавершённых прошлых сроков. Это правило заменяет прежний расчёт по календарным размещениям во всех периодах и представлениях статистики.

## 1. Статус решений и приоритет требований

Единый источник требований для реализации — это ТЗ. `concept.md` является исходной концепцией; при расхождении действуют правила этого документа.

### Уточнение 1.2: рабочий запуск без почтовых рассылок

По решению пользователя от 1 ноября 2026 года рабочий состав — **два человека: руководитель и один помощник**. Вход — по email и паролю; email служит логином. SMTP не подключается, служебные письма не отправляются. Рабочие уведомления остаются внутри приложения.

Владелец проекта вручную создаёт в Supabase Auth две подтверждённые учётные записи и закрыто назначает членство и роли. Новый пароль вводит и отправляет человек непосредственно в защищённой форме Supabase; пароли не передаются через чат, исходники или SQL. Руководитель создаётся через private.bootstrap_team; помощник связывается с той же командой как активный employee. При потере пароля восстановление выполняет владелец через Supabase, без почтовой ссылки. Пользователь с действующей сессией может менять пароль в профиле; для запуска без почты secure_password_change выключается, чтобы Auth не требовал почтовый nonce. Минимальная длина 12 символов сохраняется. Свободная и анонимная регистрация выключены.

В текущем интерфейсе нет кнопки «Забыли пароль?», формы приглашения и списка приглашений. Показано обращение к руководителю; просмотр участников, отключение с передачей задач и повторное включение работают. Режим задаётся RITM_EMAIL_DELIVERY_ENABLED=false и в сборке, и в Edge Function; запросы приглашения/повтора сервер отклоняет до административной работы.

Ранее разработанный почтовый режим сохраняется как отключаемая возможность. Ниже требования к приглашениям, письмам и одноразовым ссылкам (разделы 5.1–5.2, почтовая часть раздела 14, UC-01/03/05/06 и AC-04) действуют **только при явно включённом RITM_EMAIL_DELIVERY_ENABLED=true и настроенном SMTP**. Их реальная почтовая доставка не является условием текущего запуска. Остальные права, 48 UC/39 AC, формулы и сценарии не меняются. Дополнительные тестовые сотрудники допустимы только в изолированных проверках. Это уточнение имеет приоритет над прежними формулировками почтового режима.

Согласованные изменения относительно концепции:

- Автоперенос выполняется на следующий **рабочий** день. Суббота и воскресенье остаются видимыми в календаре.
- «Ожидает ответа» также участвует в ежедневной проверке и переносе на рабочие дни.
- Направления фиксированы: СТО, ДБК, ПРОКАТ, УК; отсутствие направления отображается как «Без направления».
- У задачи один ответственный. Чек-листов и подзадач нет.
- Есть комментарии и управление командой внутри продукта; приглашения доступны только в явно включённом почтовом режиме.
- Уведомления о работе — внутри приложения. Почтовые приглашения и восстановление выключены для текущего запуска; см. уточнение 1.2.
- Итоги можно скачать для последующего переноса в Google Презентации.
- Общее облачное хранение согласовано ранее. localStorage используется для локальных настроек, а не для общих задач.

Для полноты реализации приняты следующие настройки без дополнительных продуктовых вопросов:

| Решение | Значение первой версии |
| --- | --- |
| Команда | Одна общая команда; стартовый состав — один руководитель и один сотрудник |
| Количество пользователей | Стартовый состав не зашивается в код и не является ограничением лицензии приложения |
| Руководители | Один первоначальный руководитель; управление дополнительными руководителями через интерфейс не требуется |
| Часовой пояс | Europe/Moscow для всей команды, независимо от устройства |
| Рабочие дни | Понедельник–пятница; производственный календарь, праздники и отпуска не учитываются |
| Перенос сотрудником | Изменение разрешённой даты работы без согласования; срок сдачи сам не меняется |
| Завершение | Сразу учитывается как результат, без приёмки руководителем |
| Отчёт | Редактируемый PPTX, обзорный PNG и копирование текстовой сводки |
| История | Не удаляется автоматически; прошедшие периоды рассчитываются по состоянию на конец периода |
| Название | «Ритм» |

Обычные технические решения, не меняющие описанное поведение, разработчик принимает самостоятельно. Нельзя заменять согласованные функции заглушками, демонстрационными данными или локальной имитацией общей доски. В рабочей версии не должно оставаться TODO по перечисленным обязательным сценариям.

## 2. Назначение, состав и ограничения версии

Продукт помогает руководителю и сотрудникам планировать месяц по неделям, работать с текущим днём, контролировать сроки и видеть общий и индивидуальный прогресс. Повседневное создание задачи должно требовать минимального ввода.

Обязательные части: вход, общая доска, день/неделя/месяц, задачи и комментарии, направления, статусы и приоритеты, переносы, регулярные и длительные задачи, уведомления, итоги, экспорт, управление командой и восстановление удалённых задач.

Не входят: чек-листы, подзадачи, несколько ответственных, отдельные проекты/клиенты сверх направлений, встречи, календарь времени, трудозатраты, зависимости задач, чат, вложения, упоминания через @, push-уведомления, рабочие email-рассылки, офлайн-редактирование, импорт старых таблиц, синхронизация через экспорт/импорт и автоматическая запись в Google Презентации.

Страница размещается на GitHub Pages. Интерфейс состоит из `index.html`, `styles.css`, `app.js`, без обязательного фреймворка и сборки. Облачная часть — управляемый Supabase: Database, Auth, Realtime, Cron и Edge Functions для административных действий. Отдельный обслуживаемый сервер не создаётся. SQL-миграции, облачные функции, тесты и инструкции являются служебными материалами; ограничение трёх файлов относится к интерфейсу.

## 3. Термины и общие правила

| Термин | Определение |
| --- | --- |
| Плановая дата / период | День либо включительный интервал дней, в которые запланирована работа |
| Срок сдачи | Необязательная дата, до конца которой нужен результат; независима от плана |
| Длительная задача | Одна задача с рабочим интервалом более одного дня |
| Регулярная серия | Правило создания самостоятельных экземпляров задач |
| Экземпляр | Конкретная задача регулярной серии с собственным идентификатором и статусом |
| Самостоятельная задача | Создана сотрудником себе и не переведена руководителем под управление |
| Назначенная задача | Создана руководителем либо передана/взята под управление руководителем |
| Активная задача | «В плане», «В работе» или «Ожидает ответа», не удалена |
| Просрочка | Вычисляемый признак нарушения срока, а не отдельный статус |
| Мягкое удаление | Скрытие карточки с сохранением данных и возможности восстановления |
| Исторический план | Сохраняемые сведения о попадании задачи в дни и об изменениях плана |

Рабочая неделя начинается в понедельник. Неделя отображается до воскресенья включительно. Дата хранится как календарная дата `YYYY-MM-DD`, события — как серверные UTC-временные отметки. Отображение событий — по Москве. Нельзя получать «сегодня» простым обрезанием UTC-строки даты или доверять часам браузера для бизнес-операций.

Срок истекает в 00:00 следующего календарного дня по Москве. Завершение раньше этого момента своевременно, начиная с этого момента — с опозданием. Срок, выпавший на выходной, сам не сдвигается. Пример: срок — воскресенье, задача завершена в понедельник — есть опоздание.

## 4. Роли и матрица прав

Роли: `manager` — руководитель; `employee` — сотрудник. Пользователь без действующей сессии или активного членства не получает рабочие данные.

| Действие | Сотрудник | Руководитель |
| --- | --- | --- |
| Смотреть общую доску, задачи, комментарии, историю и итоги | Да | Да |
| Фильтровать по любому сотруднику и направлению | Да | Да |
| Скачивать общие или отфильтрованные итоги | Да | Да |
| Создать задачу себе | Да | Да |
| Назначить/переназначить другому участнику | Нет | Да |
| Изменить свою самостоятельную активную задачу | Все пользовательские поля | Да |
| Изменить свою назначенную активную задачу | Статус, описание, плановый интервал | Да |
| Изменить название, срок, приоритет, направление или повторение назначенной задачи | Нет | Да |
| Изменить чужую задачу | Нет | Да |
| Завершить свою задачу, вернуть её в работу | Да | Да |
| Отменить, удалить или восстановить свою самостоятельную задачу | Да | Да |
| Отменить, удалить или восстановить назначенную/чужую задачу | Нет | Да |
| Комментировать любую неудалённую задачу команды | Да | Да |
| Редактировать или удалять свой комментарий | Да | Да |
| Удалить чужой комментарий | Нет | Да, с записью в истории |
| Менять текст чужого комментария | Нет | Нет |
| Пригласить, отключить, повторно подключить сотрудника | Нет | Да |
| Изменить своё отображаемое имя и пароль | Да | Да |
| Самостоятельно изменить свою роль или состав направлений | Нет | Нет |

Дополнительные правила:

1. Права на задачу требуют, чтобы сотрудник оставался её текущим исполнителем. Авторство само по себе не даёт права менять переданную другому человеку задачу.
2. `management_mode=self` устанавливается только при создании сотрудником задачи себе. Создание руководителем, его переназначение или явное действие «Взять под управление» устанавливает `manager`. Обратного перевода в `self` в первой версии нет. Простое комментирование или обычный просмотр руководителем режим не меняет.
3. Если руководитель меняет защищённые поля самостоятельной задачи сотрудника, интерфейс предупреждает «После сохранения срок и приоритет этой задачи будет менять руководитель»; сохранение переводит её в `manager`.
4. «Изменить плановый интервал» не даёт права менять срок сдачи или правило повторения. Перенос отдельного экземпляра серии не переносит остальные экземпляры.
5. Завершённая/отменённая задача доступна для чтения и комментариев. Для изменения рабочих полей сначала требуется вернуть её в активный статус с записью события. Удалённую задачу комментировать нельзя.
6. Все ограничения проверяются облаком, включая разрешённые поля. Скрытие кнопок и передача роли из браузера не считаются проверкой прав.

## 5. Вход, профиль и управление командой

### 5.1. Вход и восстановление

- Экран входа: логотип/название, email, пароль, «Войти», «Забыли пароль?». Свободной регистрации нет.
- Email очищается от пробелов по краям и сравнивается без учёта регистра. Пароль не обрезается. Минимум — 12 символов; поле подтверждения обязательно при установке нового пароля.
- Успешная сессия сохраняется средствами Supabase Auth. Перезагрузка не требует повторного ввода пароля, пока сессия действительна.
- Ошибка входа не раскрывает, существует ли конкретная учётная запись. Есть понятные состояния отправки, ограничения частоты и повторной попытки.
- Восстановление отправляет служебную ссылку; публичный ответ одинаков для известного и неизвестного email. Ссылка открывает форму нового пароля, а не доску до завершения проверки.
- Пригласительная и восстановительная ссылки одноразовые. Срок действия — 24 часа; соответствующие настройки Auth и проверка срока приглашения должны быть заданы явно. Истёкшая ссылка показывает понятный экран и предложение запросить новую у руководителя/повторить восстановление.
- После обработки ссылки секреты авторизации убираются из адресной строки. Redirect URL содержит полный путь GitHub Pages к репозиторию.
- В профиле можно менять отображаемое имя и пароль; email в интерфейсе первой версии не меняется.
- «Выйти» закрывает подписки, очищает данные команды из памяти и текущую локальную сессию. На чужом устройстве повторный вход открывает данные только после авторизации.

### 5.2. Раздел «Команда»

Доступен только руководителю. Список: имя, email, роль, состояние «Приглашён / Активен / Отключён», количество активных задач и доступные действия. Остальные участники видят в фильтрах имена и роли, но не административные данные приглашений.

Приглашение: руководитель вводит имя и email; роль всегда «Сотрудник». Облако создаёт приглашение и отправляет ссылку. Пользователь устанавливает пароль и активируется. Приглашение не позволяет выбрать или повысить роль. Повторное нажатие не создаёт второго участника с тем же email.

Предусмотреть повторную отправку приглашения не чаще раза в 60 секунд и отмену ещё не принятого приглашения. Успех отправки означает принятие письма почтовым сервисом, а не подтверждение доставки. При ошибке доставки приглашение видно как неотправленное с возможностью повторить; ложного «Отправлено» нет.

При отключении сотрудника:

1. Показать количество его активных задач и незавершённых регулярных серий.
2. Если они есть — обязательно выбрать активного нового исполнителя, включая руководителя.
3. Одной согласованной операцией переназначить активные задачи и будущие серии, записать историю и закрыть членство. При ошибке не оставлять частично перенесённые задачи.
4. Завершённые, отменённые и удалённые карточки сохранить с прежним исполнителем. Исторические итоги не переписывать.
5. Новые запросы отключённого участника блокируются независимо от остаточного срока JWT; открытая страница закрывает рабочие экраны после получения события или первой проверки доступа.

Последнего руководителя отключить нельзя. Руководитель может повторно включить сотрудника; старые задачи автоматически назад не передаются. Сброс пароля выполняется служебным письмом, а не показом пароля руководителю.

## 6. Экраны, навигация и представления

### 6.1. Общий каркас

Основные разделы: «План», «Итоги»; руководителю также «Команда». Общие элементы: профиль, уведомления с числом непрочитанных, состояние соединения. «Корзина» доступна через меню плана в пределах прав пользователя.

После первого входа открывается текущий день. Руководителю по умолчанию видна вся команда, сотруднику — «Мои задачи». Это только фильтр: сотрудник может переключиться на всю команду.

Настройки вида, фильтры сотрудника/направления и группировка сохраняются по ключу пользователь+команда+версия схемы localStorage. После нового входа дата снова сегодняшняя. Служебные ссылки входа обрабатываются раньше восстановления навигации. Если localStorage недоступен, приложение продолжает работу без сохранения настроек.

### 6.2. Экран «План» на компьютере

- Верхняя панель: выбранный месяц, назад/вперёд на месяц, «Сегодня», фильтры сотрудника и направления, «Добавить задачу».
- Три компактные шкалы: выполнение плана выбранного дня, содержащей его недели и выбранного месяца. При выборе другой даты подписи и периоды обновляются; текущее число явно отмечено.
- Крупный блок выбранного дня, около 60% основной области: дата, количество задач, быстрый ввод, карточки, сворачиваемые группы выполненных и отменённых задач.
- Соседний компактный блок семи дней выбранной недели: подписи дат, небольшие карточки, количество задач. Стрелки недель меняют выбранную дату на тот же день недели ±7 дней.
- Ниже — месяц по семидневным неделям; количество строк определяется календарём, без обязательной пустой шестой недели. Соседние даты месяца приглушены, доступны для перехода.
- Нажатие дня синхронно меняет день, неделю и месяц. Переход месяца выбирает то же число, а при его отсутствии — последний день месяца.
- «Сегодня» сбрасывает дату, сохраняя выбранного сотрудника и направление.
- Задача, одновременно попавшая в день/неделю/месяц, остаётся одной записью: действие над любой карточкой обновляет все представления.

Выходные видны всегда, с мягким фоновым отличием. Создавать и вручную планировать на них можно. В недельном списке день внутри длительного интервала показывает ту же задачу с меткой «Период», а не копию.

### 6.3. Фильтры, поиск и сортировка

| Фильтр | Варианты и действие |
| --- | --- |
| Исполнитель | Вся команда / Я / конкретный участник; в истории доступны отключённые участники |
| Направление | Все / СТО / ДБК / ПРОКАТ / УК / Без направления |
| Статус | Один или несколько; по умолчанию три активных, завершённые доступны отдельной группой |
| Приоритет | Четыре категории и «Не задан»; можно выбрать несколько |
| Срок | Все / Без срока / Сегодня / Ближайшие 7 календарных дней / Просрочено |
| Поиск | Подстрока названия и описания, без учёта регистра; задержка ввода 250 мс, без поиска по комментариям |
| Группировка | Обычный список / По статусу / По приоритету |

Фильтры соединяются логическим И; значения внутри одного мультивыбора — ИЛИ. Есть «Сбросить фильтры». Отдельно объясняются состояния «В этот день нет задач» и «По фильтрам ничего не найдено».

Исполнитель и направление влияют на задачи, шкалы, итоги и экспорт. Статус, приоритет, поиск и фильтр срока влияют только на списки, а не на знаменатель прогресса. Рядом с показателями есть подсказка об этом. Отфильтрованные числители нельзя выдавать за выполнение всего плана.

Сортировка активных карточек: просроченные → со сроком сегодня → остальные; внутри блока приоритет в порядке важная+срочная, важная+несрочная, неважная+срочная, неважная+несрочная, не задан; затем ближайший срок, отсутствие срока в конце; затем время создания и ID. Завершённые — по времени завершения от новых. Ручной порядок внутри дня в первую версию не входит: перетаскивание меняет дату.

Над календарём есть ссылка «Все просроченные: N» для текущих активных задач сотрудника/направления независимо от их плановых дат. Открывает отдельный список с возможностью перейти к задаче. Его число не подменяет статистику конкретного месяца.

### 6.4. Телефон

При ширине менее 768 px — одна колонка: прогресс, выбранный день, полоса семи дат и список недели, сворачиваемый месяц. Горизонтальная прокрутка всей страницы не допускается. Недельный список заменяет тесную сетку; выбранная дата и выходные остаются понятными.

Добавление доступно закреплённой кнопкой. Подробности задачи открываются полноэкранной панелью. Все функции доступны нажатием; drag-and-drop не обязателен на телефоне. Нижние действия не перекрываются экранной клавиатурой и системной безопасной областью.

## 7. Модель задачи, ввод и статусы

### 7.1. Пользовательские поля и валидация

| Поле | Правило |
| --- | --- |
| Название | 1–200 символов после обрезки краёв, обязательно |
| Начало работы | Обязательно технически, автоматически выбранный день |
| Конец работы | По умолчанию равен началу; не раньше начала, интервал не более 366 календарных дней |
| Ответственный | Ровно один активный участник; автоматически текущий пользователь либо выбранный руководителем сотрудник |
| Направление | Одно из четырёх либо null = «Без направления» |
| Важность/срочность | Оба признака заданы совместно либо оба null; начально «Приоритет не задан» |
| Срок | Необязательная календарная дата |
| Описание | Необязательно, до 10 000 символов, обычный текст |
| Статус | При создании «В плане» |
| Повторение | Нет / Каждый день / По рабочим дням / Еженедельно / Ежемесячно |

Поддерживаемые даты — 2000-01-01…2100-12-31. Создание или ручное изменение плана задним числом запрещены: новая дата начала не раньше сегодня. Прошлые события работы нельзя подставлять ручным вводом. Даты срока могут быть в прошлом: при сохранении есть предупреждение, но такой срок разрешён. Срок раньше планового начала также разрешён после предупреждения, так как перенос не должен исправлять нарушение автоматически.

Кириллица, переносы строк описания и эмодзи поддерживаются. HTML не исполняется; описание и комментарии не являются Markdown-редактором. http/https-ссылки в тексте можно открывать с безопасными атрибутами, остальные схемы не превращаются в активные ссылки.

### 7.2. Быстрое создание

Ввод названия и Enter создают обычную однодневную задачу. Приоритет, срок, описание и повторение не требуются. Раскрытие дополнительных полей не очищает название.

Подстановка исполнителя: сотрудник всегда создаёт себе; руководитель — выбранному в фильтре конкретному участнику, иначе себе. Если сотрудник смотрит чужой список, поле явно показывает его самого; после создания выводится сообщение, что карточка скрыта текущим фильтром, с действием «Показать мои».

Направление подставляется из конкретного фильтра; при «Все» — «Без направления». Автоматические значения видны до сохранения. Быстрое создание в прошлом периоде предлагает сегодня и не записывает задачу задним числом.

На время отправки кнопка блокируется. Повтор запроса с тем же ключом операции не создаёт дубликат. Форма очищается только после подтверждённого сохранения. Копирование существующей задачи отдельной командой не требуется.

### 7.3. Карточка и подробности

Карточка: название, имя исполнителя, направление, статус, приоритет, срок/просрочка, метка длительности/повтора/переноса при наличии, количество комментариев. Необязательные пустые поля не занимают строки. Открытие подробностей показывает полное описание, даты, действия, комментарии и журнал.

Уточнение оформления от 2 ноября 2026 года: в карточках и подробностях статусы показаны текстовыми цветными плашками. «В плане» — бледно-голубой, «В работе» — жёлтый, «Ожидает ответа» — оранжевый, «Просрочено» — красный, «Выполнено» — зелёный, «Отменено» — серый. Размер текста плашки не менее 14 px, контраст текста к фону не ниже 4,5:1. Значение понятно по тексту, а не только по цвету.

«Просрочено» — дополнительная автоматическая плашка по серверному признаку overdue, рядом с основным активным статусом. Она не выбирается вручную и не заменяет «В плане», «В работе» или «Ожидает ответа». Появляется после окончания даты сдачи по Москве, исчезает при завершении/отмене либо разрешённом изменении срока на неистёкший. Удалённые задачи не помечаются просроченными; в историческом просмотре действует серверный исторический признак. Для задач без срока плашки просрочки нет. Схема БД, переходы статусов, фильтры и расчёт процентов не меняются.

Журнал содержит автора действия, московское время и изменённые значения: создание, назначение, изменение полей, статусы, переносы, отмена, удаление, восстановление, действия с серией и комментариями. Системный перенос подписан «Автоматически». Записи журнала не редактируются через продукт.

### 7.4. Переходы статусов

Три активных статуса могут переходить друг в друга и в «Выполнено». Для «Ожидает ответа» причина не обязательна; рядом предлагается добавить комментарий. Завершение записывает серверные `completed_at`, `completed_by` и состояние срока на момент завершения.

Из любого неудалённого статуса можно перейти в «Отменено» только при наличии прав на отмену; причина 1–1 000 символов обязательна. Отмена не считается выполнением.

Возврат из «Выполнено» или «Отменено» переводит в «В работе». Для отменённой задачи требуются права на её восстановление; для выполненной достаточно права менять собственный статус либо роли руководителя. Если текущий рабочий интервал уже закончился, продолжение назначается на сегодня, когда это рабочий день, иначе на ближайший следующий рабочий. История прежнего завершения/отмены остаётся.

Кнопка «Завершить» показывает уведомление «Отменить действие» на 10 секунд. Оно вызывает обычное повторное открытие с проверкой версии. Позже остаётся команда «Вернуть в работу». Повторное нажатие уже выполненного завершения не создаёт новое событие.

## 8. Планирование, переносы и повторения

### 8.1. Ручное планирование

Перенос доступен из карточки, подробностей, недельной сетки и месячного календаря. В команде «Перенести» есть сегодня, следующий рабочий день и выбор даты. Перенос на выходной вручную разрешён; в прошлое — запрещён. На исходную дату без изменений — пустая операция, без нового события.

Для активного текущего интервала из N дней перенос его начала на дату X задаёт конец X+N−1 календарных дней. Во время ещё действующего длительного интервала это перенос всего интервала, а не создание второй задачи. Исходные даты сохраняются в истории. Отдельное изменение конца периода выполняется в подробностях в пределах прав на плановый интервал.

Срок, статус, исполнитель, направление и идентификатор от переноса не меняются. При плане позже срока показывается предупреждение, но перенос не блокируется. Для завершённых/отменённых сначала требуется повторное открытие.

При drag-and-drop допустимая дата подсвечивается; недоступная показывает причину. До ответа облака карточка помечена «Сохраняется»; при ошибке возвращается на исходное место. Перетаскивание не должно открывать форму неожиданно. На компьютере то же действие доступно без мыши через меню.

### 8.2. Автоперенос

Пусть D — сегодняшняя дата команды. `next_workday_on_or_after(D)` — D, если это понедельник–пятница, иначе ближайший понедельник. Проверка выполняется каждый календарный день для активных задач с концом текущего рабочего интервала раньше D.

- Текущий интервал такой задачи заменяется однодневным продолжением на `next_workday_on_or_after(D)`. Для бывшей длительной задачи исходный интервал остаётся в истории, показывается метка «Продолжение».
- Предыдущий план сохраняется; новая задача и новое повторение не создаются. После такого продолжения ручной перенос сдвигает именно однодневное продолжение.
- Будущие интервалы, завершённые, отменённые и удалённые задачи не меняются.
- «Ожидает ответа» переносится по тем же правилам и сохраняет статус.
- Проверка в субботу переносит незавершённую пятницу на понедельник. Воскресная проверка не переносит её ещё раз, поскольку понедельник ещё впереди.
- Задача, вручную поставленная на субботу, остаётся в субботу до окончания этого дня; при воскресной проверке переходит на понедельник.
- В отсутствие запусков несколько дней выполняется последовательное восполнение пропущенных рабочих дат плана. Промежуточные записи нужны для верных дневных итогов; целевая карточка после восстановления находится на ближайшем допустимом текущем/будущем рабочем дне.

Плановый запуск — ежедневно в 00:00 по Москве (`0 21 * * *` при UTC-настройке Cron; проверить фактический часовой пояс задания при развёртывании). Допуск появления результата — 5 минут при доступном сервисе. При входе, возврате вкладки и смене даты вызывается проверка актуальности. Одновременные запуски сериализуются по команде; операция идемпотентна.

Нельзя позволять браузеру задавать произвольную дату автопереноса: она получается из серверного времени. Восполнение плановых дат не выдумывает выполнение задач или смену исполнителя задним числом.

### 8.3. Регулярные задачи

Настройки: тип повторения, дата первого экземпляра, необязательная дата конца включительно, дни недели для еженедельного режима, число месяца для ежемесячного. Интервал повторения фиксирован: каждый день/каждую неделю/каждый месяц, без «каждые N» в первой версии.

- «Каждый день» включает выходные; «По рабочим дням» — только понедельник–пятница.
- Еженедельный режим требует минимум один день, включая возможность выбрать выходной.
- Для ежемесячного числа 29–31, которого нет в месяце, используется последний день месяца. Привязка к исходному числу сохраняется: после февраля правило 31 снова даёт 31 марта.
- Длительность экземпляра равна исходному календарному интервалу; пересекающиеся экземпляры разрешены, поскольку представляют разные результаты.
- Если есть срок, у серии сохраняется смещение срока от исходного начала в календарных днях; оно применяется к каждому экземпляру. Перенос отдельного экземпляра смещение серии не меняет.
- Экземпляр содержит неизменяемые `series_id` и `occurrence_date` исходного расписания. Уникальность этой пары предотвращает дубликаты, в том числе после удаления/переноса экземпляра.
- Завершение одного экземпляра не завершает серию. Незавершённые прошлые экземпляры переносятся независимо; будущие не подавляются.
- Экземпляры создаются облаком для текущего и следующего месяца, а также по запросу просмотра другого месяца. Для длительных экземпляров учитывается начало раньше выбранного месяца. Открытие далеко будущего месяца не выполняет автоперенос в будущее.
- После простоя восполняются положенные по расписанию экземпляры начиная с последней успешной проверки. Их прошлый план отражает правило серии; невозможно создавать экземпляры до создания самой серии.

Редактирование: «Только эту задачу» создаёт исключение экземпляра; «Эту и будущие» доступно только при полном праве редактировать серию. У назначенной руководителем серии сотрудник может менять разрешённые поля конкретного экземпляра, но не шаблон.

«Эту и будущие» действует от исходной даты выбранного экземпляра, не раньше сегодня. Если исходная дата экземпляра уже в прошлом, для него доступно «Только эту»; изменение серии с сегодняшнего дня выполняется отдельной командой «Изменить будущие повторения». Прошлые и завершённые экземпляры не переписываются. Перед сохранением показывается число будущих затронутых задач и предупреждение, что их индивидуальные изменения будут заменены. Сохраняющиеся даты расписания обновляют существующие ID; исчезающие будущие экземпляры помечаются системно заменёнными, новые создаются с уникальным ключом. Системно заменённые будущие экземпляры не считаются пользовательскими отменами. Экземпляры, чей день уже наступил, сохраняют фактическую историю плана.

При остановке серии пользователь выбирает «Завершить повторение после этой даты»; будущие ещё не наступившие экземпляры убираются из будущего плана, текущие активные остаются. Удаление одной карточки само по себе серию не останавливает. Отмена отдельного экземпляра также не отменяет следующие.

### 8.4. Удаление и восстановление

Удаление требует подтверждения с названием задачи. В облаке устанавливаются `deleted_at`, `deleted_by`, сохраняются прежний статус и история; физического DELETE задач нет. Карточка исчезает со всех досок, действие можно отменить 10 секунд либо восстановить позже из корзины.

Корзина сотрудника содержит только доступные ему для восстановления самостоятельные задачи; руководитель видит все. Есть поиск и дата удаления. Восстановление возвращает прежний статус. Если он активный и план уже прошёл — создаётся продолжение по правилам автопереноса. Завершённая восстанавливается завершённой без новой даты выполнения.

Удаление не служит способом скрыть невыполненный результат из отчёта: если дата результата уже наступила, задача сохраняется в знаменателе. Для признания работы ненужной используется «Отменить» с причиной. Удалённая до наступления даты результата задача из будущего результата исключается. Календарная история размещений сохраняется; после восстановления история не дублируется.

## 9. Комментарии и уведомления

### 9.1. Комментарии

Любой активный участник комментирует любую неудалённую задачу команды, включая завершённую или отменённую. Комментарий — 1–4 000 символов после обрезки краёв. Видны автор, дата, текст и отметка «Изменён» при редактировании. Порядок — от старых к новым; подгрузка по 50, переход к новым сообщениям доступен сразу.

Автор может редактировать/удалять свой комментарий. Руководитель может удалить чужой, но не переписать его от чужого имени. При удалении остаётся метка «Комментарий удалён», прежний текст сохраняется только в защищённом журнале для руководителя. Обычный сотрудник не получает удалённый чужой текст через API истории. Черновик не теряется при сетевой ошибке; двойная отправка с тем же ключом не создаёт две записи.

Уведомление создаётся только при публикации нового комментария. Изменение текста не рассылает новое. При конфликте одновременного редактирования комментария действует проверка версии.

### 9.2. Центр уведомлений

Колокольчик открывает список личных уведомлений, фильтр «Все / Непрочитанные», «Прочитать все». Просмотр списка сам по себе не помечает всё прочитанным; открытие конкретного уведомления помечает его и открывает задачу. Статус чтения общий между устройствами пользователя.

| Событие | Получатели | Условие |
| --- | --- | --- |
| Назначена/передана задача | Новый исполнитель | Кроме случая, когда он сам выполнил назначение |
| Новый комментарий | Текущий исполнитель и автор задачи | Без автора комментария, без дубля при совпадении получателей |
| Завершена назначенная задача | Её автор-руководитель | Если завершил другой человек |
| Срок завтра | Исполнитель | Один раз за задачу и текущую версию срока |
| Срок сегодня | Исполнитель | Один раз за задачу и текущую версию срока |
| Есть просроченные задачи | Исполнитель; руководитель получает общую сводку | Не более одной сводки пользователю за календарный день |

Учитываются только активные участники и неудалённые активные задачи для напоминаний о сроке. Изменение срока создаёт новую версию основания напоминания; старое уведомление не удаляется. При массовом переназначении из-за отключения сотрудника вместо десятков отдельных уведомлений создаётся одна сводка получателю.

Напоминания формируются облаком при ежедневной проверке и проверке актуальности после входа. Создание задачи, изменение её срока или повторное открытие дополнительно проверяют актуальное основание напоминания, даже если ежедневное задание уже прошло. Закрытая страница не показывает push или системное уведомление; при следующем входе накопленные записи видны в центре. Нет звуков, навязчивых всплывающих окон и запросов разрешения браузера на push.

Уведомления нельзя прочитать за другого пользователя. Если задача удалена, ссылка показывает «Задача удалена» и восстановление только при наличии права. При отключённом членстве данные задачи не раскрываются.

## 10. Расчёты, исторический план и экран «Итоги»

### 10.1. Единая модель времени и истории

Расчёты выполняются облаком и возвращаются одним согласованным снимком. Запрещено считать прошлые месяцы из текущих полей задачи или усреднять проценты сотрудников.

Период задаётся полуоткрытым интервалом `[начало первого дня, начало дня после последнего)` по Москве. День — одна дата; неделя — понедельник–воскресенье; месяц — календарный месяц. Для текущего и будущего периода момент расчёта T — серверное «сейчас», для прошедшего — состояние непосредственно перед концом периода. Событие ровно на границе относится к следующему периоду.

У каждого изменения есть фактическое время записи и время действия для бизнеса. Для действий человека они равны серверному времени. Только системная процедура может восполнить пропущенное действие расписания с его положенной датой; это отдельно помечается. Человек не может подставить `completed_at`, исполнителя события или более раннее время изменения.

Перед расчётом облако материализует необходимые регулярные экземпляры и восполняет пропущенные системные операции. Для известного ранее расписания будущий план не должен зависеть от того, открывал ли кто-то этот месяц. Начальное состояние такого экземпляра известно с момента создания соответствующего правила серии, фактическое время его вставки хранится отдельно. Новая серия не создаёт план или факты до своего создания.

### 10.2. Что означает попадание в план результата (уточнение 1.4)

Календарное размещение отражает дни работы, но знаменатель результата определяется сроком сдачи. При отсутствии срока используется конец запланированного интервала. Дата создания сама по себе в план дня не включает.

Для периода берётся историческое состояние задачи на T (для закрытого периода — строго до конца периода). Множество B содержит уникальные ID с датой результата внутри периода, а также задачи с более ранней датой результата, не выполненные к началу периода или выполненные внутри него. Поэтому долг учитывается до дня выполнения включительно; после этого в последующие дни не входит. Отменённые исключаются из знаменателя P. Системно заменённые будущие экземпляры не учитываются. Удалённые до наступления даты результата исключаются; удаление в дату результата или позже не скрывает невыполненную обязанность. Все даты московские, выходные остаются календарными днями.

Длительная задача со сроком 3 ноября не снижает процент 2 ноября. Досрочно выполненная задача сохраняется выполненной в плане своего срока; факт досрочного выполнения показывается отдельно в день выполнения, без увеличения дневного числителя и знаменателя. В неделе/месяце каждый ID считается один раз. Процент периода не является средним дневных процентов.

Ответственность и направление плана берутся на T; событийные результаты — на момент события. Будущая человеческая правка не меняет историческое состояние закрытого периода. Правило 1.4 применяется ко всем пересчитываемым периодам. Ранее скачанные файлы не меняются; старые серверные снимки отчётов истекают при обновлении версии расчёта.

### 10.3. Формулы и показатели

| Показатель / ключ | Точное определение |
| --- | --- |
| План `planned_count` | Количество ID в P |
| Выполнено из плана `plan_done_count` | ID из P со статусом «Выполнено» на T |
| Выполнение `progress_percent` | `100 × plan_done_count / planned_count`, отображать до одного знака после запятой, целые без «,0» |
| Осталось `remaining_count` | `planned_count − plan_done_count`; включает удалённые незавершённые записи плана |
| Статусы `status_planned_count` / `in_progress_count` / `waiting_count` | Соответствующие активные статусы ID из P на T, без мягко удалённых |
| Удалённые незавершённые `deleted_unfinished_count` | Мягко удалённые невыполненные ID из P; отдельная составляющая остатка |
| Сделано заранее `early_done_count` | Уникальные ID действующих завершений периода, совершённых раньше московской даты результата из состояния в момент завершения; независимо от P |
| Выполнено за период `actual_done_count` | Число уникальных ID с действующим на T событием завершения внутри периода, независимо от P |
| Просрочено `overdue_count` | Неудалённые активные ID из P, у которых момент истечения срока не позже T |
| С опозданием `late_done_count` | ID из фактического выполнения, завершённые начиная с момента истечения срока, действовавшего при завершении |
| Отменено `cancelled_count` | Уникальные ID с действующей на T пользовательской отменой внутри периода; системная замена будущей серии сюда не входит |
| Перенесено `moved_task_count` | Уникальные ID с изменением плановой даты внутри периода; `manual_moved_task_count` и `auto_moved_task_count` — отдельные подмножества, их пересечение не суммировать как разные задачи |
| Новые задачи `created_count` | ID из B, впервые известные по плану внутри периода; для регулярных учитывается момент появления правила/соответствующей новой даты в нём, а не ленивой вставки |
| Добавлено в план по ходу периода `added_to_plan_count` | ID из B, впервые включённые в план этого периода после его начала; это не обязательно новые задачи |

Когда `planned_count=0`, процент — null, подпись «Нет запланированных задач», шкала нейтральная. Отсутствие плана не равно выполнению 100%. В счётчиках отдельно различаются «выполнено из плана» и «выполнено фактически».

Проверочная идентичность: planned_count = plan_done_count + status_planned_count + in_progress_count + waiting_count + deleted_unfinished_count. Нарушение означает ошибку расчёта; остаток не выводится как сумма только видимых карточек.

Если задачу завершили заранее, она считается выполненной в будущем плане, где остаётся её действующее размещение; фактическое выполнение относится к реальной дате завершения. Если её вернули в работу в том же периоде, прежнее завершение не входит в действующий факт этого периода. Повторное завершение внутри одного периода даёт один ID. Повторное открытие после конца периода не меняет его сохранённый результат; новое завершение в другом периоде учитывается там как повторный результат и имеет метку «Повторно завершена».

Действующим завершением считается такое событие, после которого до T не было перехода в активный статус или «Отменено». Мягкое удаление не отменяет завершение. Для закрытого периода учитываются только переходы до его конца. Показатели событийных действий — фактическое завершение, переносы, отмены — фильтруются по исполнителю и направлению в момент соответствующего события; показатели состояния плана — по состоянию на T. Комментарий и действие человека от имени руководителя не подменяют исполнителя задачи.

Фактический результат относится к исполнителю и направлению на момент соответствующего завершения, а не к человеку, нажавшему кнопку от имени руководителя. Исполнитель/направление в таблице плана относятся к T. Эти основания подписаны в подсказках; нельзя смешивать их в одном неподписанном столбце.

Позднее изменение срока не исправляет прежнюю своевременность задним числом. В метрике просрочки прошлого периода используется исторический срок. Отмена в следующем месяце не уменьшает прошлый знаменатель. Ошибочно выполненную задачу можно открыть повторно, но править время старого факта через интерфейс нельзя.

### 10.4. Экран итогов

Выбор периода: «День / Неделя / Месяц», по умолчанию текущий месяц; переходы назад/вперёд и возврат к текущему периоду. Для месячного режима — выбор месяца и года. Фильтры сотрудника и направления согласованы с экраном плана.

Содержимое:

- Основные карточки: план, выполнено из плана и процент, выполнено фактически, осталось, просрочено, отменено.
- Дополнительные числа: добавлено по ходу периода, в работе, ожидает ответа, с опозданием, перенесено вручную/автоматически, удалённые незавершённые в плане.
- Для месяца — диаграмма и таблица по неделям, интервалы на границах ограничены выбранным месяцем. Для недели — по дням; для дня — распределение по статусу. Подписи границ явные.
- Таблица по сотрудникам с планом, выполнением плана, процентом, фактическими результатами и просрочкой. Отключённый участник показывается, если имеет данные периода.
- Таблица направлений в фиксированном порядке СТО, ДБК, ПРОКАТ, УК, Без направления. При фильтре направления остаётся выбранная строка.
- Нажатие числа открывает список ID, из которых оно рассчитано, с тем же моментом снимка, основанием и доступом к подробностям.

Уникальные задачи считаются в каждом подпериоде отдельно. Поэтому сумму недель для длительных/перенесённых задач нельзя выдавать за месячный итог; у таблицы есть соответствующая подпись. Для неполного месяца явно показываются дата и время расчёта. Месячные отчёты не ранжируют сотрудников по «лучше/хуже».

## 11. Скачивание итогов для Google Презентаций

Кнопка «Скачать отчёт» расположена на экране «Итоги». Она использует выбранные период, сотрудника и направление и один серверный снимок. Фильтры списков по статусу/поиску/приоритету в отчёт не попадают. Перед скачиванием показывается краткое описание состава и формата.

### 11.1. PPTX — основной редактируемый формат

Файл `ritm_YYYY-MM-DD_YYYY-MM-DD_<employee-or-all>_<direction-or-all>.pptx`, формат слайдов 16:9. Имена частей файла безопасны, без персонального email. Для полного месяца допускается короткое имя периода `YYYY-MM`.

Состав презентации:

1. Обзор: период, выбранные фильтры, время снимка, основные KPI и процент выполнения плана.
2. Динамика: недели месяца или дни недели, план и выполнено, подпись об уникальности задач.
3. Сотрудники: показатели по выбранным сотрудникам; таблица переносится на дополнительные слайды при необходимости.
4. Направления: показатели четырёх направлений и «Без направления» с учётом фильтра.
5. Выполненные за период задачи: название, исполнитель, направление, фактическая дата, отметка опоздания.
6. Незавершённые просроченные задачи плана: название, исполнитель, направление, срок и статус.

Пустой блок содержит «Нет задач» и не является ошибкой. Строки таблиц не обрезаются молча: применяется перенос и разбиение на слайды, не более 10 обычных строк на слайд; для длинных названий строк меньше. Содержание целиком остаётся читаемым. Минимальный размер основного текста — 14 pt, таблиц — 12 pt. Комментарии, пароли, email и полный журнал в отчёт не включаются.

Текст, KPI, таблицы и простые графические элементы создаются редактируемыми объектами PPTX, а не скриншотом всей страницы. Библиотека — PptxGenJS 4.0.1, браузерный bundle; загрузка и версии определены в разделе 11.3. Импорт в Google Презентации выполняется пользователем после скачивания; подключения Google-аккаунта к планировщику не требуется. Возможности браузерной генерации описаны в [PptxGenJS](https://github.com/gitbrent/PptxGenJS); работа с PowerPoint в Google Презентациях — в [справке Google](https://support.google.com/docs/answer/9310378?hl=en).

### 11.2. PNG и текстовая сводка

PNG `ritm_<period>_summary.png`: один обзорный слайд 1920×1080, непрозрачный светлый фон, период, фильтры, время снимка, основные KPI и небольшая динамика. Все надписи на русском. Он строится из данных отчёта, а не снимком текущего экрана телефона. Изображение можно вставить в существующую Google Презентацию; его элементы отдельно не редактируются.

«Скопировать сводку» копирует обычный текст: период и фильтры, план, выполнение из плана, процент, фактическое выполнение, остаток, просрочка, отмены и показатели по направлениям. При недоступном Clipboard API показывается выделяемый текст с инструкцией копирования.

Создание PNG можно реализовать стандартным Canvas API. Формирование файлов происходит в браузере из одного DTO отчёта, без отправки данных стороннему генератору. Для PPTX разрешена отложенная загрузка зависимости; её ошибка не блокирует работу доски и PNG. При ошибке скачивания сохраняются выбранные настройки и кнопка повторения. На мобильном устройстве допускается системный диалог сохранения/поделиться.

### 11.3. Браузерные зависимости и фиксированный макет

| Назначение | Реализация | Закреплённый адрес |
| --- | --- | --- |
| Облако и авторизация | `@supabase/supabase-js` 2.118.0, UMD | [supabase.js](https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2.118.0/dist/umd/supabase.js) |
| PPTX | `pptxgenjs` 4.0.1, bundle с JSZip | [pptxgen.bundle.js](https://cdn.jsdelivr.net/npm/pptxgenjs@4.0.1/dist/pptxgen.bundle.js) |
| PNG | Canvas 2D, `toBlob` и Blob URL | Встроенный браузерный API; html2canvas и серверный рендер не используются |

Версии закреплены по [метаданным Supabase JS](https://registry.npmjs.org/@supabase/supabase-js/2.118.0) и [релизу PptxGenJS 4.0.1](https://github.com/gitbrent/PptxGenJS/releases/tag/v4.0.1). Перед выпуском проверить загрузку обоих точных bundle в целевых браузерах; при замене версии обновляются ТЗ/README и повторяются проверки экспорта/авторизации. Нельзя самовольно подставлять `latest`. Supabase загружается до работы приложения; PPTX-библиотека — один раз при первом экспорте, с повтором после ошибки. Blob URL освобождается после завершения скачивания.

Общие координаты PPTX: 13,333×7,5 дюйма; безопасные поля слева/справа 0,45. Заголовок — x=0,45, y=0,35, h=0,5, 26 pt; подзаголовок — y=0,9, h=0,4, 14 pt. Основная область — y=1,5…6,6. Футер — y=6,95, h=0,25, 10 pt: «Ритм · период · снимок» слева, «N / Всего» справа. Числа/подписи используют Arial; фон и цвета — токены раздела 12.

На обзорном слайде шесть KPI-карточек: три колонки, два ряда; ширина 4,01, горизонтальный промежуток 0,2, высота 1,4, верхние координаты рядов 1,6 и 3,2. KPI: план; выполнено из плана вместе с процентом; фактически выполнено; осталось; просрочено; отменено. Нижняя область y=5,1…6,6 — прогресс и краткая динамика. При нулевом плане выводится текст, а не ложные 100%.

Для таблиц: ширина 12,433; заголовок 0,38; строка минимум 0,44 дюйма. Высота строки = максимум 0,44 и высота всех её текстовых строк при 12 pt и межстрочном интервале 14,4 pt плюс 0,08 сверху и снизу. Высоту определяет самая высокая ячейка, измеренная с фактической шириной колонки и переносом слов. Для длинного слова разрешён посимвольный перенос. Заголовок таблицы повторяется на каждом слайде.

Пагинация выполняется **до записи файла**: на слайд помещается не более 10 строк и только столько, сколько целиком укладывается вместе с заголовком в 5,1 дюйма основной области. Следующая целая строка переносится на новый слайд того же блока с пометкой «Продолжение». Размер шрифта не уменьшается ниже 12 pt. В исключительном случае строки выше целой страницы текст делится на последовательные строки-продолжения с тем же ID; символы не отбрасываются. Общее количество слайдов и номера проставляются после расчёта страниц.

Для списков задач ширины колонок: название 4,9; исполнитель 2,0; направление 1,2; дата/срок 1,7; результат/статус 2,633. Таблицы метрик используют ту же суммарную ширину; подписи повторяются при продолжении. При нехватке ширины подпись переносится, а значение не перекрывает соседнюю ячейку.

PNG повторяет обзорный слайд: система координат пересчитывается пропорционально в 1920×1080, приблизительно 144 px на дюйм; текст рисуется отдельными Canvas-вызовами из DTO. Все обязательные KPI/фильтры остаются видимыми при длинном имени: имя переносится в подзаголовке, не поверх карточек. Это отдельный макет отчёта, не снимок DOM страницы.

## 12. Дизайн, доступность и состояния интерфейса

Светлый спокойный интерфейс: фон `#F5F6F8`, карточки `#FFFFFF`, основной текст `#24303F`, акцент `#55657E`, выполнение `#3F6655`, предупреждение `#8A6245`, просрочка `#9B4B50`. Это токены, их оттенки можно скорректировать ради контрастности. Системный шрифт, основной размер не менее 16 px; минимум 14 px для вторичных подписей.

Не использовать яркие полноэкранные заливки, рекламные блоки, рейтинги, звуки и анимацию наград. Короткие переходы до 200 мс допустимы с учётом `prefers-reduced-motion`. Шкалы сопровождаются числом и текстом, различия статусов не зависят только от цвета.

Контрольные ширины: 360, 390, 768, 1024 и 1440 px. На 768–1023 px допустима одна колонка с раскрываемой неделей, от 1024 — крупный день и соседняя неделя. Целевые зоны касания — минимум 44×44 px, текст не перекрывается значками.

Формы имеют подписи, ошибки рядом с полем и сводную ошибку операции. Диалоги удерживают фокус, закрываются Escape, возвращают фокус инициатору; закрытие с несохранёнными изменениями требует выбора «Остаться / Закрыть без сохранения». Enter сохраняет быстрый ввод, но в многострочном описании создаёт новую строку. Tab-порядок логичен, фокус видим, у иконок есть доступные имена.

Обязательные состояния: начальная загрузка, пустая команда/день/выборка/отчёт/корзина, сохранение, успешное сохранение, ошибка валидации, отказ в доступе, конфликт версии, потеря сети, истёкшая сессия, ошибка загрузки зависимости экспорта, недоступная конфигурация облака и открытая удалённая карточка.

Если облако не настроено, показывается экран «Планировщик ещё не подключён» с понятной информацией для администратора. Запрещено незаметно переключаться на локальные задачи и создавать впечатление работающей общей доски.

## 13. Данные и обязательные ограничения облака

### 13.1. Логические сущности

Физические имена ниже рекомендуемые; если они меняются, карта соответствий должна быть в README. Тип ID — UUID, счётчики версий — целые числа. Внешние ключи сохраняют историю при отключении пользователя; удалять Auth-пользователя вместе с его рабочими данными нельзя.

| Сущность | Минимальное содержимое |

Фиксированные значения: роли `manager/employee`; статусы `planned/in_progress/waiting/done/cancelled`; направления `sto/dbk/rental/uk/null`; режим управления `self/manager`. Русские подписи определены выше. Пользовательские изменения справочников в первой версии отсутствуют.

Снимок события должен позволять восстановить на любую дату статус, план, срок, исполнителя, направление, удаление и управление. Одного списка «поле изменено» без старых значений недостаточно. Изменение рабочей записи, запись события, обновление плана и создание связанных уведомлений выполняются в одной транзакции.

Важность и срочность допускают только оба null или оба boolean. plan_end ≥ plan_start, длительность ≤366, обязательные текстовые поля проверяются и в БД. Повторение не указывает отключённого исполнителя. ID задач/комментариев уникальны; `(series_id, occurrence_date)` уникальна среди всех экземпляров, включая удалённые и заменённые. День плана не обязан иметь одну физическую строку на всю жизнь: повторное размещение хранится новой ревизией, расчёт уникализирует task_id.

`created_at` — реальная вставка, `effective_created_at` — момент известности экземпляра по правилу раздела 10. Для обычной задачи они равны. Реальное время никогда не подменяется ради вида старой даты. Системная процедура получает значения для восполнения из истории, а не из аргумента браузера.

Журнал и ревизии правил должны находиться в закрытой схеме либо иметь эквивалентные ограничения прямого чтения/записи. API выдаёт безопасную историю по правам, без удалённого чужого текста комментария. При мягком удалении комментария его публичное тело очищается; старое тело остаётся в закрытом событии. Удаление карточки задачи не является механизмом конфиденциальности: доступные команде исторические итоги могут содержать её название.

История задач не очищается по расписанию. Кэш снимков отчёта действует 24 часа, затем может удаляться: это не удаление истории или самого отчёта из скачанного файла. Результаты операций сохраняются минимум 30 дней; создание задачи/комментария дополнительно защищено уникальным постоянным ключом создания, чтобы повтор после истечения кэша не создал дубль.

Индексы: team+исполнитель+статус, team+текущие даты, team+deadline, task+время/последовательность события, дата размещения+task, task+комментарии, recipient+read_at+created_at, уникальности повторов, приглашений и ключей операций. Изолировать данные team_id во всех связях, запретить ссылку задачи на участника другой команды.

### 13.2. Права на данные

- Включить RLS на всех доступных через API таблицах. У анонимного клиента нет SELECT/INSERT/UPDATE/DELETE рабочих данных.
- Чтение текущих задач требует активного членства той же команды. Комментарии доступны участникам по задаче, уведомления — только получателю, приглашения — руководителю, снимок отчёта — создавшему его участнику.
- Прямую запись в задачи, историю, размещения, серии и состав команды из браузерного клиента запретить. Рабочие мутации проходят проверяемые RPC; административные Auth-вызовы — Edge Function.
- RPC проверяет серверную личность, активное членство, роль, разрешённый набор полей, состояние задачи и ожидаемую версию. Не доверять присланным author_id, actor_id, role, effective_at и вычисляемым метрикам.
- Если используется `SECURITY DEFINER`, явно ограничить EXECUTE, установить фиксированный безопасный search_path и проверять доступ внутри функции. Повышенные права функции сами по себе не являются авторизацией.
- И публичные чтения, и RPC/функции должны повторно проверять активность участника, чтобы старый JWT отключённого сотрудника не давал доступа.
- Публичный ключ приложения допустим в `app.js`. Secret/service-role ключи, SMTP-пароли и приватные токены находятся только в секретах облака. В GitHub, localStorage настроек, URL и логи интерфейса они не попадают.

Настройка разрешений и функций основывается на официальных материалах: [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [функции БД](https://supabase.com/docs/guides/database/functions), [защита Edge Functions](https://supabase.com/docs/guides/functions/auth). Конкретные продуктовые ограничения этого ТЗ сохраняются независимо от выбранного API-шаблона.

## 14. Контракты операций и обработка конфликтов

### 14.1. Общий контракт

Каждая мутация получает `operation_id` UUID, созданный один раз на пользовательское намерение, и `expected_version` для изменения существующей сущности. Если запрос завершился по тайм-ауту, повторяется тот же ID и то же тело. Новый ID создаётся только для нового намерения. Тот же ID с другим телом возвращает ошибку, а не переисполняет запрос.

Общий ответ успешной мутации: `operation_id`, `server_time`, обновлённая сущность/сущности с новыми версиями, разрешённые действия, признак уже выполненного повтора. Имена RPC ниже являются контрактом поведения; допускается объединить их в одну типизированную функцию, сохранив все ограничения.

| Операция | Основные параметры | Результат и проверки |
| --- | --- | --- |
| `sync_workspace` | team_id | Серверное сегодня, актуальность расписаний/переносов; клиент не задаёт будущую дату выполнения |
| `get_planner` | выбранная дата, фильтры сотрудника/направления, фильтры списка, cursor при подгрузке | Один снимок: страницы карточек дня/недели, агрегаты месяца, шкалы, серверное время и счётчик общих просроченных; не весь журнал и не все месячные карточки |
| `get_task_detail` | task_id | Текущие данные, allowed_actions, версия; понятное состояние мягкого удаления |
| `get_task_history` | task_id, cursor, limit≤50 | Безопасная история по времени, с учётом скрытия удалённого текста комментариев |
| `create_task` | поля раздела 7, operation_id | Задача, плановые размещения, событие, уведомление назначения при необходимости |
| `update_task` | task_id, patch, expected_version, operation_id | Проверка каждого изменённого поля и режима управления; пересчёт плановых размещений |
| `move_task` | task_id, новая дата начала, expected_version, operation_id | Сдвиг текущего интервала без изменения срока/статуса |
| `change_status` | task_id, новый статус, причина при отмене, expected_version, operation_id | Дата выполнения только серверная; разрешённый переход, план продолжения при повторном открытии |
| `delete_task` / `restore_task` | task_id, expected_version, operation_id | Мягкое удаление/возврат, история и план в одной транзакции |
| `update_series` / `stop_series` | series_id, scope, граница, patch, expected_version, operation_id | Проверка полного права, пересборка будущего расписания без потери истории |
| `list_comments` | task_id, cursor, limit≤50 | Комментарии и метки удаления в устойчивом порядке |
| `create_comment` | task_id, текст, operation_id | Комментарий и дедуплицированные уведомления |
| `update_comment` / `delete_comment` | comment_id, expected_version, operation_id, текст при изменении | Авторство/роль, версия, закрытая история |
| `get_notifications` / `read_notifications` | cursor/filter либо список ID/«все до времени» | Только собственные записи; массовое чтение не затрагивает более новые уведомления |
| `get_report` | тип/границы периода, employee_id либо all, direction либо all | Создаёт неизменяемый снимок на 24 часа: метрики, таблицы, snapshot_id/at |
| `get_report_rows` | snapshot_id, metric_key, cursor, limit≤50 | Строки именно этого снимка; изменения после snapshot_at не смешиваются с ним |
| `get_export_data` | snapshot_id | Полный DTO того же снимка для PPTX/PNG/текста без скрытого ограничения количества строк |
| `list_deleted_tasks` | фильтры, cursor, limit≤50 | Корзина в пределах прав на восстановление |
| `update_profile` | своё имя либо новый пароль через Auth | Нельзя поменять роль или другого пользователя |

Чтения списков используют устойчивый курсор, а не случайный порядок. В каждой прошлой ячейке календаря карточки показывают состояние на конец именно её дня; они явно помечены «История». Действия из прошлой сетки не двигают старую запись: открываются текущие подробности с подписью «Текущее состояние». Переносить можно текущую активную карточку на сегодня/будущее. На будущей доске показывается текущее известное состояние будущего плана; ещё не произошедшие автопереносы туда не прогнозируются.

Для снимка отчёта параметры, данные метрик и строки замораживаются вместе. Истёкший снимок предлагает обновить отчёт; сохранённый файл не зависит от срока кэша. Все чтения снимка требуют действующего доступа на момент запроса. Не выдавать действующий снимок отключённому пользователю только по знанию ID.

### 14.2. Административная Edge Function

Действия: `invite_employee`, `resend_invitation`, `cancel_invitation`, `list_team_admin`, `disable_employee`, `enable_employee`. Каждое требует действительного пользовательского JWT и проверки роли руководителя по БД. Проверка токена выполняется до использования административного клиента.

Сервисный ключ используется только внутри функции. CORS разрешает фактический HTTPS-origin GitHub Pages и явно заданный адрес локальной разработки; произвольные origin не разрешаются. CORS не заменяет проверку JWT/членства. Значения redirectTo берутся из конфигурации и не принимаются как произвольный URL от браузера.

Операции Auth и БД не образуют общую транзакцию, поэтому приглашение выполняется с журналируемыми состояниями и безопасным повтором: сначала регистрация намерения, затем вызов Auth, затем фиксация результата. При частичном сбое повтор продолжает то же приглашение. Нельзя оставлять активного участника без подтверждённой связи с приглашённым Auth-пользователем.

При отключении членство, переназначение задач и серий фиксируются одной транзакцией БД. Дополнительный отзыв сессии/блокировка Auth выполняются после неё с повтором при ошибке; даже до их завершения RLS уже закрывает данные. Приглашение по email поддерживается доверенным Auth Admin API; см. [документацию приглашений](https://supabase.com/docs/reference/javascript/auth-admin-inviteuserbyemail).

### 14.3. Ошибки и гонки

| Код | Что показывает интерфейс | Что сохраняется |
| --- | --- | --- |
| `VALIDATION_ERROR` | Ошибки конкретных полей | Все введённые значения |
| `UNAUTHENTICATED` | Предложение войти снова | Черновик в памяти до выхода пользователя |
| `ACCESS_DENIED` | «Недостаточно прав» / «Доступ отключён» | Не отправлять повтор без изменения доступа |
| `NOT_FOUND` | «Задача не найдена» без раскрытия чужих данных | Переход назад |
| `VERSION_CONFLICT` | «Задача изменилась у коллеги»; новый вариант и свои несохранённые изменения | Оба варианта, без автоматической перезаписи |
| `ALREADY_DELETED` | Состояние удалённой карточки | Возможность восстановления по правам |
| `RATE_LIMITED` | Время, когда доступен повтор | Формы и параметры |
| `OPERATION_ID_REUSED` | «Не удалось повторить операцию» | Логирование технической причины, без автоматической смены ID |
| `SNAPSHOT_EXPIRED` | «Обновите отчёт перед скачиванием» | Фильтры отчёта |
| `NETWORK_OR_SERVICE_ERROR` | Соединение потеряно/сервис недоступен, «Повторить» | Черновик, ID операции и старое подтверждённое состояние |

Конфликт: пользователь видит актуальную задачу и может применить свои изменения повторно после явного просмотра. Автоматическое «последний сохранивший победил» запрещено. Если конфликт возник при переносе, карточка возвращается на актуальную дату. Повтор запроса после неизвестного результата сначала проверяет/использует сохранённый результат operation_id.

### 14.4. Численные ограничения частоты

Прикладные ограничения ниже — требования продукта, а не обещание безлимитного тарифа провайдера. Лимиты применяются облаком: UI-таймер не считается защитой. Пользователь определяется по проверенному JWT и активному членству, а не по присланному ID/заголовку.

| Группа | Лимит |
| --- | --- |
| Чтение плана/списков | 120 запросов за 60 секунд на пользователя и 600 на команду |
| Все рабочие мутации суммарно | 60 новых операций за 60 секунд на пользователя и 300 на команду |
| Создание комментариев, дополнительно к мутациям | 20 за 60 секунд на пользователя |
| Новый снимок отчёта | 6 за 60 секунд на пользователя и 30 за час на команду; получение уже созданного снимка относится к обычному чтению |
| Административная Edge Function | 20 запросов за 60 секунд на руководителя |
| Приглашения/повторные отправки | 5 писем за 15 минут на руководителя, 20 за сутки на команду и не чаще одного за 60 секунд на конкретный email |
| Полная проверка sync_workspace | Не чаще одного прохода за 30 секунд на команду, кроме смены московской даты; повтор возвращает последнее состояние, если оно актуально, а не выполняет тот же проход |

Окна фиксированные, отсчитываются по UTC от границ соответствующей минуты/часа/суток; 15-минутные — от 00/15/30/45. Проверка и увеличение счётчика атомарны. Для одной операции применяются все соответствующие пределы. Повтор уже зафиксированного operation_id возвращается до расходования лимита новых операций. Плановые внутренние задания не расходуют пользовательские счётчики.

Для Auth настроить проект: отправка служебных писем с собственным SMTP — не более 30 за час на проект; восстановление/повтор письма одному пользователю — интервал 60 секунд; публичные Auth-запросы регистрации/восстановления/повторной отправки и verify — до 30 за 5 минут на IP; token endpoint, включая пароль и обновление сессии, — до 150 за 5 минут на IP с ёмкостью всплеска 30. Это отдельный механизм Supabase Auth; см. [официальные ограничения Auth](https://supabase.com/docs/guides/auth/rate-limits). Свободная регистрация остаётся выключенной независимо от лимита.

IP нельзя передавать в SQL из браузера и считать проверенным. Для прикладных RPC достаточно лимита проверенного пользователя/команды; глобальный IP-лимит всего PostgREST здесь не обещается. Достоверный IP для Auth ограничивается инфраструктурой провайдера. Не использовать неподтверждённый X-Forwarded-For как личность пользователя.

При превышении Edge/Auth возвращает 429, RPC — структурированный `RATE_LIMITED` с `retry_after_seconds`; если транспорт поддерживает собственный HTTP-статус, также 429. На экране: «Слишком много запросов. Повторите через N секунд». Данные и черновики сохраняются, автоматический цикл повторов без паузы запрещён.

### 14.5. Граница SQL и интерфейса: обязательные расчётные функции

Автоперенос, генерация повторений, исторический знаменатель, сроки и агрегаты реализуются в PostgreSQL. Фронтенд выбирает фильтры, отправляет команды, рисует DTO и формирует файлы из DTO. Он не пересчитывает показатели альтернативным алгоритмом, не переносит задачи локально по своим часам и не пишет историю отдельными HTTP-запросами.

Следующие три публичные сигнатуры фиксированы. Остальные операции раздела 14.1 могут иметь внутреннюю декомпозицию, документированную в README.

| Функция | Вход | Обязательные поля data ответа |
| --- | --- | --- |
| `public.sync_workspace` | `p_team_id uuid` | `today` date, `timezone`, `processed_through` date, `moved_task_count` integer, `generated_count` integer, `state_version` bigint, `checked_at` timestamptz |
| `public.get_planner` | `p_team_id uuid`, `p_selected_date date`, `p_filters jsonb`, `p_cursor text DEFAULT null` | `selected_date`, `today`, `timezone`, `day_tasks`, `week_days`, `month_cells`, `progress` для day/week/month, `overdue_total`, `next_cursor`, `snapshot_at` |
| `public.get_report` | `p_team_id uuid`, `p_period_type text`, `p_period_start date`, `p_employee_id uuid DEFAULT null`, `p_direction text DEFAULT 'all'` | `snapshot_id`, `snapshot_at`, `expires_at`, `period`, `filters`, `metrics`, `by_subperiod`, `by_employee`, `by_direction` |

Возвращаемый SQL-тип — jsonb, формат ответа ниже. `p_period_type` — day/week/month. Для week начало обязано быть понедельником, для month — первым числом; некорректная граница отвергается, а не молча сдвигается. Конец вычисляет сервер. `p_direction` — all/none/sto/dbk/rental/uk; none означает direction IS NULL. `p_employee_id=null` — вся команда, конкретный UUID — участник той же команды, включая исторически отключённого.

`p_filters`: `employee_id` uuid/null, `direction` с теми же кодами, `statuses` массив кодов, `priorities` массив important_urgent/important_not_urgent/not_important_urgent/not_important_not_urgent/unset, `deadline_filter` all/none/today/next_7_days/overdue, `query` string, `group_by` list/status/priority. Для отсутствующих полей — значения раздела 6; неизвестные поля/коды — VALIDATION_ERROR. Карточка DTO содержит ID, version, пользовательские поля раздела 7, имена участников, derived-признаки overdue/late/continuation, allowed_actions и признак исторического состояния.

`metrics` содержит все ключи раздела 10.3; численности — integer≥0, progress_percent — number/null. В каждой строке by_employee/by_direction есть ID/код, отображаемая подпись и те же метрики. `by_subperiod` добавляет границы подпериода. Крупные списки фактов читаются по snapshot_id, не из нового независимого расчёта. Экспорт получает полный DTO вместе со списками фактических завершений/просрочек того же снимка.

Успешный ответ имеет оболочку `ok=true`, `data`, `meta.schema_version=1`, `meta.server_time`. Ошибка — `ok=false`, `error.code`, `error.message`, необязательные `error.field_errors`, `error.retry_after_seconds` и `error.latest_entity`; `data` отсутствует. Мутации добавляют внутрь data operation_id, entity/entities, allowed_actions и idempotent_replay. Дата/время ответа не берутся из клиента.

Внутренние функции, недоступные браузерному EXECUTE:

- `private.next_workday_on_or_after(p_date date) RETURNS date`: чистое правило понедельник–пятница, например 2026-10-31 → 2026-11-02.
- `private.maintain_team(p_team_id uuid, p_effective_today date) RETURNS jsonb`: блокировка команды, материализация повторений, восполнение пропущенных дат и переносы, фиксация результата одним согласованным проходом. Cron и публичный sync передают вычисленную сервером московскую дату.
- `private.calculate_period(p_team_id uuid, p_start date, p_end_exclusive date, p_as_of timestamptz, p_employee_id uuid, p_direction text) RETURNS jsonb`: множества B/P, метрики и основания строк строго по разделу 10. Вызывается из get_report/get_planner после актуализации. Режим закрытого периода применяет исключительную верхнюю границу, а не включает события следующего дня.
- `private.maintain_all_teams() RETURNS jsonb`: серверная московская дата, последовательный вызов maintain_team для активных команд, сводка processed_teams/moved_task_count/generated_count/errors. Доступ только у владельца задания, без публичного EXECUTE.

Единственное задание Cron с именем `ritm_daily_maintenance` и расписанием `0 21 * * *` при UTC вызывает private.maintain_all_teams: 21:00 UTC соответствует 00:00 Europe/Moscow. Повторное применение миграции обновляет это задание, а не создаёт второе. Параллельный публичный sync использует ту же private.maintain_team и блокировку, не отдельный алгоритм. Тестовый вызов с подставленной датой допускается только доверенному тестовому окружению; в рабочий API такой параметр не добавляется.

## 15. Синхронизация, сеть и устойчивость

Источник истины — облачная БД. Рабочие задачи, комментарии, статистика и непрочитанные уведомления не хранятся исключительно в localStorage. Локальные черновики формы первой версии живут в памяти открытой страницы; при ошибке связи не исчезают, но восстановление после закрытия браузера не обещается. Пароли в черновики не сохраняются.

После входа: проверка сессии → активное членство → актуализация системных операций → один согласованный снимок экрана → Realtime-подписки. Изменения задач, комментариев, уведомлений и членства вызывают обновление затронутых данных и показателей. Повторные события с той же версией игнорируются.

При обрыве сети отображается постоянный, но ненавязчивый индикатор «Нет связи. Данные могут быть устаревшими». Подтверждённый экран остаётся видимым. Новые мутации не складываются в скрытую офлайн-очередь; пользователь может оставить текст в форме и повторить после восстановления. Внешнее изменение не затирает открытую форму: появляется предупреждение и действует проверка версии.

После восстановления сети, возврата вкладки и восстановления WebSocket выполняется повторное чтение, а не предположение, что все события были доставлены. Резервная проверка актуальности в видимой вкладке — каждые 60 секунд. В фоновой вкладке можно приостановить её, сохранив обязательную проверку при возвращении. При смене московской даты пересчитываются «сегодня», просрочка, периоды и переносы.

Повторяемые операции блокируются транзакционными блокировками/уникальными ключами. Автоперенос и изменение серии не могут создать две версии одного экземпляра. Массовые операции выполняются с серверной проверкой прав на каждую изменяемую сущность.

Встроенные задания наблюдаемы: время успешного запуска, число обработанных задач/экземпляров и код ошибки без секретов. При сбое catch-up следующий запуск продолжает корректно; невозможно отмечать дату успешно обработанной до фиксации данных. Просмотр истории и отчётов выполняет нужное восполнение до расчёта либо явно сообщает, что актуальные данные получить не удалось.

## 16. Нефункциональные требования

- Браузеры: актуальные и предыдущие основные версии Chrome, Edge, Firefox, Safari; мобильные Chrome Android и Safari iOS. Нет требования устанавливать приложение.
- HTTPS обязателен. Использовать относительные пути к CSS/JS, чтобы приложение работало в подпапке репозитория GitHub Pages. Роутинг внутри страницы — hash либо обычное состояние без серверного rewrite.
- Типовой объём для проверки: до 20 активных участников, 10 000 экземпляров задач и 100 000 событий; исходно используются руководитель и один сотрудник; изолированные тесты могут содержать дополнительных участников. Нельзя загружать весь журнал для отрисовки одного дня.
- При доступном прогретом облаке и соединении 10 Мбит/с: полезный экран после входа до 3 секунд, ответ обычного чтения/сохранения до 2 секунд для 95% операций на контрольном наборе; локальная реакция на нажатие до 100 мс. Задержка внешнего сервиса отображается состоянием загрузки, а не блокировкой всей страницы.
- Изменение коллеги в активной подключённой вкладке видно обычно до 3 секунд; при отсутствии Realtime — после резервного обновления. Допуск ежедневного задания — до 5 минут при доступном облаке.
- Список задач подгружается порциями не более 100 карточек; комментарии/журнал/корзина — по 50. Числовые итоги считают весь набор на сервере, а не только загруженную страницу.
- Экспорт типового месяца до 500 строк — целевое время до 10 секунд на обычном компьютере. Больший отчёт показывает ход формирования и не обрезает данные без уведомления. Не вводить неподписанный лимит «первые 100 задач».
- Все даты/числа форматируются по `ru-RU`; проценты и число задач имеют единые правила округления. Названия месяцев русские.
- XSS исключается безопасным выводом обычного текста. Входные данные и права проверяются облаком. Технические ошибки не раскрывают токены, приватные данные и внутренние stack trace пользователю.
- Зависимости: официальный Supabase JS-клиент и PptxGenJS в точных версиях и формате раздела 11.3. Дополнительные тяжёлые UI-фреймворки не требуются. CDN-ссылки без фиксированной версии запрещены; сбой экспортной библиотеки не ломает планирование.
- Исходные бизнес-данные и секреты не включаются в репозиторий. Начальный рабочий экран пустой. Тестовые задачи создаются только в тестовой среде.

## 18. Проверяемые критерии приёмки

Критерии применяются к изолированной тестовой команде. UC описывает цель и путь пользователя, AC — проверяемое условие реализации; столбец связей устраняет необходимость повторно описывать шаги. Подготовка окружения и команды запуска оформляются в тестовой документации результата реализации, а не как пользовательские функции.

## 22. Согласованная доработка: личная динамика и поддержка (2 ноября 2026)

Применяется к обеим учётным записям, без привязки логики к именам. На главной доске — компактный график текущей московской недели, понедельник–воскресенье: для каждого дня запланировано/выполнено из плана. Используются существующие серверные формулы и история, все направления; фильтры списка не меняют личную динамику. Будущие и выходные дни обозначены, числа и текст доступны без наведения. Сотрудник получает свой блок; руководитель — свой и активных сотрудников. Остальные общие отчёты сохраняют прежние права.

По понедельникам–пятницам с 17:45 Europe/Moscow показывается крупная закрываемая карточка по центру без звука (оформление уточнено в разделе 23). Получатель видит личное сообщение, руководитель также видит сообщение сотруднику в блоке динамики и личном центре уведомлений. Состояние прочтения/показа у получателя и руководителя независимо. Руководителю автоматически всплывает его собственный итог; сообщения сотрудников доступны в их карточках и уведомлениях.

Категории: весь непустой план выполнен — поздравление; выполнено не меньше половины, но не весь план — похвала за продвижение; меньше половины — мягкая поддержка. Сравнение ведётся по числителю/знаменателю до округления; одна из одной — полный успех. Вес/приоритет задач не учитывается. При пустом плане дословно: «Сегодня не было запланированных задач. Не забывай ставить себе даже небольшие задачи - из маленьких дел складывается большой успех!».

Тексты непустого плана: полный результат — «Все задачи выполнены! Молодец, так держать!»; не меньше половины — «Отличный результат! Есть куда стремиться.»; меньше половины — «Не вешай нос. Завтра можно продолжить — шаг за шагом.». Имя и дата итога показываются отдельно, рядом — выполнено/запланировано и процент.

Если приложение закрыто, при следующем входе показывается один последний завершённый рабочий день, без очереди пропущенных сообщений. До 17:45 текущего рабочего дня берётся предыдущий рабочий день; после — текущий. Не показывать результат за день до вступления участника в команду. При позднем выполнении в тот же день текст/показатели обновляются, но баннер повторно не появляется; после смены московской даты действуют обычные правила закрытого периода ТЗ. Повторный вход, перезагрузка, другая вкладка/устройство не сбрасывают подтверждённую отметку показа. Закрытая/скрытая вкладка и открытый диалог не должны расходовать показ невидимого баннера. При потере ответа возможен пропуск всплытия, но сообщение остаётся в карточке и уведомлениях; ровно один фактический просмотр человеком не обещается.

Уведомление создаётся сервером, клиентские часы и роль из браузера не являются основанием расчёта. Cron — будни 14:45 UTC (17:45 Москвы); первый вход и видимое резервное обновление восполняют пропуск. Использовать существующую notifications, без новой таблицы. Нельзя при обновлении результата возвращать read_at в null. Новые RPC проверяют живое членство, ограничивают частоту, не раскрывают сообщения других сотрудников обычному сотруднику.

Приёмка дополнения: проверить обе роли и запреты напрямую; неделю через границу месяца; 17:44:59/17:45:00 Москвы и пятницу–понедельник; пустой план и категории 0/ниже 50/ровно 50/полный результат; позднее завершение; повторный и одновременный запрос показа; пропущенные дни и новые аккаунты; сохранение отметки между сессиями; безопасность текста и отсутствие повторных всплытий при обновлении; адаптивность 360/390/768/1440 px. Основные 48 UC/39 AC сохраняют свои номера; проверки дополнения оформляются отдельно.

## 23. Уточнение 1.4: результат по срокам и заметная карточка (2 ноября 2026)

Согласовано пользователем после обсуждения рабочего примера: начало 2 ноября, конец и срок 3 ноября. При одной выполненной сегодняшней задаче результат 2 ноября — 1/1, 100%. Правила раздела 10.2 в редакции 1.4 имеют приоритет над прежним расчётом по размещениям; действуют для шкал, графиков, отчётов, сообщений и новых выгрузок, в том числе прошлых периодов.
